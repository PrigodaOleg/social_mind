# Состояние: подход, расположение бизнес-логики, передача между экранами, тестирование

## Выбранный подход

- Управление состоянием — библиотека `bloc` (`^9.2.1`) с обёрткой `flutter_bloc` (`^9.1.1`) для UI, заявлены в `pubspec.yaml:59, 65`.
- Каждая фича описывается тройкой классов в одном файле: `<Feature>Bloc extends Bloc<<Feature>Event, <Feature>State>`, `<Feature>State`, `sealed class <Feature>Event extends Equatable` — пример `TaskListBloc extends Bloc<TaskEvent, TaskListState>` (`lib/state/task_list/task_list.dart:6`), `TaskListState` (`lib/state/task_list/task_list.dart:79`), `sealed class TaskEvent extends Equatable` (`lib/state/task_list/task_list.dart:96`).
- Состояние — обычный immutable-по-конвенции класс (без `Equatable`) с методом `copyWith`, принимающим функции-фабрики полей: `TaskListState.copyWith({Map<String, Task> Function()? tasks})` (`lib/state/task_list/task_list.dart:87-93`), `DomainListState.copyWith({Map<String, Domain> Function()? domains})` (`lib/state/domain_list/domain_list.dart:111-117`), `ContactListState.copyWith({Map<String, User> Function()? contacts})` (`lib/state/contact_list/contact_list.dart:118-124`).
- События — `final class <Action>Requested extends <Feature>Event`, регистрируются в конструкторе BLoC через `on<Event>(_handler)`: `on<TaskListStateInitRequested>(_onStateInit); on<TaskAddRequested>(_onTaskAdd); on<TaskCompletionRequested>(_onComplited); on<TaskSubmitionRequested>(_onSubmitted); on<TaskChangingRequested>(_onChanged);` (`lib/state/task_list/task_list.dart:11-15`).
- BLoC существует для трёх фич: список задач (`lib/state/task_list/task_list.dart`), список доменов (`lib/state/domain_list/domain_list.dart`), список контактов (`lib/state/contact_list/contact_list.dart`); все экспортируются через `lib/state/state.dart:3-5`.
- Страницы без изменяемого состояния (не требующие перерисовки по данным) не используют BLoC и остаются `StatelessWidget`: `LoginPage` (`lib/ui/pages/login.dart:22`), `SaveUserCredentialsPage` (`lib/ui/pages/login_user_save_credentials.dart:6`).
- Одна страница использует локальный `StatefulWidget`-стейт вместо BLoC: `CreateUserPageState extends State<StatefulWidget>` с полями `User? user; String? secret;`, обновляемыми через `setState(...)` (`lib/ui/pages/login_user_create.dart:15-21, 40-42, 49-51, 61-63, 69-72`).

## Где живёт бизнес-логика

- Обработчики событий BLoC (`_on...`) содержат бизнес-логику фичи и обращаются к `Repository`, но не к хранилищам напрямую: `TaskListBloc._onComplited` строит `changedTask = event.task.copyWith(isCompleted: event.isComplited)` и вызывает `await repository.saveModel(changedTask)` (`lib/state/task_list/task_list.dart:42-51`).
- `TaskListBloc._onSubmitted` связывает новую задачу с родителем через модель, а не через отдельный метод репозитория: `final parent = repository.getModel<Model>(parentId); parent!.linkTo(changedTask);` (`lib/state/task_list/task_list.dart:58-60`).
- `DomainListBloc._onCreation` создаёт домен и линкует его к пользователю через модель: `var newDomain = Domain(originatorId: me.id, title: event.title); await me.linkTo(newDomain, listenerId);` (`lib/state/domain_list/domain_list.dart:64-65`).
- `DomainListBloc._onDeletion` отвязывает домен от пользователя через `await me.unlinkFrom(domainToDelete);`, затем перечитывает список через `_repo.getModels<Domain>(me.domainsIds, listenerId)` (`lib/state/domain_list/domain_list.dart:87-92`).
- `ContactListBloc._onStateInit` реализует агрегацию из нескольких моделей: читает домены пользователя (`_repo.getModels<Domain>(me.domainsIds, listenerId)`), собирает `participantsIds` всех доменов и по ним читает пользователей (`_repo.getModels<User>(userIds, listenerId)`) — `lib/state/contact_list/contact_list.dart:56-63`.
- Часть бизнес-логики (линковка модели, синхронизация, разрешение конфликтов) находится не в BLoC, а в самих моделях и в `Repository`: `Model.linkTo`/`Model.linkFrom`/`Model.unlinkFrom` вызывают `Repository.instance.saveModels(...)`/`Repository.instance.deleteModel(...)` (`lib/repository/models/models.dart:122-153`); логика ребейза и мержа конфликтов — в `Repository._rebaseTransaction`/`_rebaseModel` (`lib/repository/repository/repository.dart:728-811`).
- Некоторые обработчики событий — заготовки без реализации (тело — только комментарий): `ContactListBloc._onInvitation`, `_onHandshake`, `_onCreateUserProjection`, `_onUserSync`, `_onDomainSync` — `lib/state/contact_list/contact_list.dart:66-108`.

## Как состояние передаётся между экранами

- `Repository` создаётся один раз в `AppRouterDelegate` (`Repository repository = Repository();` — `lib/ui/navigation.dart:85`) и передаётся в конструктор каждой строящейся страницы через `Function.apply(_routes[route.path] ?? unknownRoute.constructor, [repository], ...)` — `lib/ui/navigation.dart:104-110`. Тем самым один и тот же экземпляр `Repository` доступен всем страницам без отдельного провайдера состояния поверх `MaterialApp`.
- BLoC создаётся заново на каждой странице внутри `BlocProvider`, а не передаётся между экранами: `BlocProvider(create: (context) => TaskListBloc(repository: repository, parentId: id ?? repository.myId ?? ''), child: const TaskListView())` — `lib/ui/pages/task_list.dart:27-29`.
- Данные, которыми экран параметризуется при переходе, передаются как аргументы маршрута, а не как состояние BLoC: `TaskListPage(this.repository, {super.key, this.id})`, где `id` берётся из `route.args` при построении страницы — `lib/ui/pages/task_list.dart:15-23`, `lib/ui/navigation.dart:104-110`.
- Переход с возвратом значения использует стандартный `Navigator.pop(value)`/результат `showModalBottomSheet`, а не общий BLoC: `LoginPage` открывает `SaveUserCredentialsPage` через `showModalBottomSheet` и получает `bool? isPerformed` результатом — `lib/ui/pages/login.dart:42-48`; `LoginUserExistingPage` возвращает `User` через `n.pop(tryingUser)` — `lib/ui/pages/login_user_existing.dart:35-37`.
- Между несколькими экземплярами навигационного стека состояние переносится через `Repository.lastNavStack` (сеттер вызывается при каждом переходе в `AppRouterDelegate.pushNamed`: `repository.lastNavStack = navStack;` — `lib/ui/navigation.dart:151-155`), а восстанавливается при старте через `SplashScreen.backgroundTask` → `App.locateUser(repository)` → `repository.lastNavStack` → `AppNavigatorState.replaceNavigationStack(...)` — `lib/app.dart:12-21`, `lib/ui/pages/splash_screen.dart:27-34`, `lib/ui/navigation.dart:35-38, 175-178`.
- Обратная связь от `Repository` к нескольким живым BLoC одновременно идёт через callback-подписки `addSyncListener`, а не через общий стрим состояния: `_repo.addSyncListener((id, item) { ... add(DomainSyncRequested(domains: {id: item})); }, ...)` в `DomainListBloc._onStateInit` (`lib/state/domain_list/domain_list.dart:35-51`), аналогично в `ContactListBloc._onStateInit` (`lib/state/contact_list/contact_list.dart:35-54`); подписка снимается в `close()` каждого BLoC (`lib/state/domain_list/domain_list.dart:24-29`, `lib/state/contact_list/contact_list.dart:22-27`).

## Как тестируется

- Тестов непосредственно для BLoC-классов (`TaskListBloc`, `DomainListBloc`, `ContactListBloc`) в репозитории нет; пакет `bloc_test` не подключён (отсутствует в `pubspec.yaml`), поиск `blocTest`/`bloc_test` по `test/` не дал результатов.
- Тестируется слой, на который опирается бизнес-логика BLoC — `Repository`, в файле `test/repository_test.dart` (502 строки).
- Для теста `Repository` подставляются моки `LocalStorage`/`RemoteStorage` через наследование и `@override`: `class MockLocalStorage extends LocalStorage { @override Future<int> storeItems(...) {...} ... }` (`test/repository_test.dart:6-58`), `class MockRemoteStorage extends RemoteStorage { @override Future<int> saveItems(...) {...} ... }` (`test/repository_test.dart:60-109`).
- Специализированные моки покрывают конкретные сценарии: `DenyingRemoteStorage extends MockRemoteStorage` с флагом `deny` для симуляции `RemoteStorageWriteCollision` (`test/repository_test.dart:111-121`), `TrackingRemoteStorage extends RemoteStorage` записывает переданные аргументы `init`/`auth`/`createUserAndAuth` для последующих `expect(...)` (`test/repository_test.dart:125-159`), `ConfigurableLocalStorage extends LocalStorage` позволяет задать текущего локального пользователя через `meUser` (`test/repository_test.dart:162-179`).
- Для обхода реального создания `FirebaseStorage` по строковому ключу `'FirebaseRealtimeDatabase'` используется подкласс `TestRepository extends Repository`, переопределяющий `knownRemoteStorages` на тестовую фабрику: `late final knownRemoteStorages = <String, Function()>{'FirebaseRealtimeDatabase': () => testStorage};` (`test/repository_test.dart:184-197`).
- Тесты сгруппированы по методу `Repository`: `group('Repository init', ...)` (`test/repository_test.dart:200-231`), `group('Repository initRemoteStorages', ...)` (`test/repository_test.dart:233-251`), `group('Repository authRemoteStorages', ...)` (`test/repository_test.dart:253-...`), `group('Repository createUserRemoteStorages', ...)` (`test/repository_test.dart:276-...`), `group('Repository tryLogin', ...)` (`test/repository_test.dart:320-...`), `group('Repository', ...)` с тестами `syncWithRemoteStorage` (простая синхронизация, повтор, коллизия, отсутствие изменений, ребейз, ребейз с конфликтом, отказ доступа) (`test/repository_test.dart:358-...`).
- Проверки в тестах — стандартный `expect(actual, expected)` из `flutter_test`, без сторонних matcher-библиотек: `expect(localStorage.initCalled, true); expect(r.late, false);` (`test/repository_test.dart:205-206`).
- Чистая логика без внешних зависимостей (`JsonHelper.setDeep`/`getDeep` из `lib/repository/models/models.dart:164-212`) тестируется отдельно и без моков в `test/models_test.dart` (`group('JsonHelper', ...)`, `test/models_test.dart:6-43`).
