# Инварианты реестрового конвейера (спецификация правил БД)

Документ описывает **суть** правил синхронизации, не зависящую от конкретного
бэкенда. Эталонная реализация для RTDB — `database/database.rules.json`.
Для каждого нового хранилища (Firestore, Supabase, Appwrite) правила должны
воспроизводить **те же инварианты**, выраженные средствами этого бэкенда.

## Раскладка данных

- `models/$mid` — модели (User, Domain, TaskList, Task, ContactList, ...).
- `registries/$rid` — реестры: `metadata` (id, parentId), `lastIdx`
  (индекс головы цепочки), `transactions/$tidx` (цепочка транзакций).

## Два класса моделей (бизнес-правило проекта)

Реестры существуют **только у контейнеров** — `User` и `Domain`:

1. **Контейнер** (User, Domain): несёт собственное поле `registryId`
   и собственный реестр (`registries/$rid` с `metadata.parentId == $mid`).
2. **Дочерняя модель** (Task, TaskList, Contact, ...): поля `registryId`
   не имеет. Все её изменения фиксируются в реестре **родительского
   контейнера**: клиент кластеризует пачку по корневому контейнеру
   (подъём по `parents` до User/Domain, `_clusterItemsByParent`) и пишет
   её одной атомарной записью вместе с новой транзакцией этого реестра.

## Инвариант 1 — append-only цепочка транзакций

1. Транзакция с индексом `$tidx` принимается только при
   `$tidx == lastIdx + 1` (genesis: `lastIdx` не существует, `$tidx == 0`).
2. `prevId` новой транзакции обязан ссылаться на `id` текущей головы
   цепочки — «чужая» транзакция поверх существующей истории невозможна.
3. `lastIdx` растёт монотонно: запись запрещает уменьшение
   (`!data.exists() || newData.val() > data.val()`).

Следствие: устаревший клиент, не видевший чужих транзакций, не может
записать свою — его `$tidx` не продолжит голову, его пачка отвергается
**целиком** (атомарность мультилокационной записи).

## Инвариант 2 — контейнер пишется только через свежую транзакцию

Запись `models/$mid` контейнерного типа (несёт `registryId`) разрешена,
только если:

1. `registryId` непуст и указывает на реестр;
2. `lastIdx` этого реестра **вырос в той же пачке** (genesis: 0 на пустом
   реестре) — голая запись контейнера без транзакции отвергается;
3. `$mid` стоит в `changes` **новой головы** цепочки (проверка по проекции
   `newData` — транзакция и модель пишутся одним атомарным `update()`).

Следствие: «перетереть» свежие данные устаревшей копией контейнера
невозможно — копия, не видевшая чужих транзакций, не упомянута в
актуальной голове.

Для **дочерних моделей** ограничение на уровне одного узла невозможно
(RTDB не умеет разрешить реестр родителя из map `parents`) — их защита
пакетная: контракт клиента (атомарная пачка модель + транзакция
контейнера) плюс инвариант 1, отбивающий устаревшую пачку целиком.
Бэкенды с join/подзапросами (Firestore, Supabase, Appwrite) могут
проверить связь «модель → контейнер → реестр → голова» и для дочерней
модели напрямую — это строже, желательно при портировании.

## Инвариант 3 — консистентность связей и таблица типов

- `parents/$pid` требует, чтобы родитель существовал и ссылался обратно
  на `$mid` одним из своих link-полей: `children/$mid`, `domainsIds/$mid`,
  `tasks/$mid`, `contactList/$mid` (у разных типов обратная ссылка живёт
  в разных map; см. `Model.link` и переопределения в ContactList/TaskList).
- Значение `parents/$pid` — строка **типа родителя**
  (`parents[from.id] = from.type`).
- `children/$chid` требует, чтобы ребёнок существовал и содержал
  обратную ссылку `parents/$mid`.
- **Таблица типов** — допустимые пары «родитель → ребёнок»:

  | Родитель | Дети |
  |---|---|
  | User | Domain, TaskList, ContactList |
  | Domain | TaskList, Task, Project |
  | Project | TaskList |
  | TaskList | Task |

  Глубина иерархии правилом не ограничена: каждая связь валидируется
  одним и тем же правилом на своём уровне, поэтому цепочка
  Domain → Project → TaskList → Task (глубина 3) проходит, и новые
  уровни добавляются строками в таблицу.
- Пустые Map-поля (`children`, `parents`) НЕ пишутся: `update()` с `{}`
  превращается в `null` и стирает существующий узел — клиент пропускает
  пустые Map при сериализации батча.

## Контракт клиента (Repository)

1. Каждая запись модели идёт в атомарном `update()` вместе с транзакцией
   реестра её контейнера: модели кластера + `registries/$rid/{
   transactions/$tidx, lastIdx}` одной мультилокационной записью
   (разбиение по кластерам недопустимо: модель может ссылаться на модель
   другого кластера, обе записи тогда отвергаются правилами).
2. `registryId` проставляется только контейнерам (User, Domain) до записи
   и сериализуется только в их JSON.
3. Клиент пишет `lastIdx` в пачке только при добавлении новой транзакции
   (значение = новый индекс головы), поэтому запись всегда строго вверх;
   повторная запись того же значения правилами отвергается, т.е.
   перезапись не-головых транзакций невозможна в принципе.
4. Коллизия записи (отказ правил) → перечитать голову реестра, ребейз
   локальных изменений на неё, повторить транзакцию (см.
   `syncWithRemoteStorage` / `_rebaseTransaction`).

## Заметки для портирования

- **RTDB-ограничение**: `.validate` не умеет «diff» (старое против
  нового значения ключа в whole-object записи) и join'ов — поэтому
  (а) защита дочерних моделей пакетная (см. инвариант 2), (б) проверка
  кворума приглашений остаётся за серверной частью.
- В RTDB `.write`-правила складываются по OR с родительскими, а корневой
  `.write` здесь широкий (time-gate) — ограничение выражается только
  через `.validate` (он обязателен независимо от `.write`).
- Арифметика над отсутствующим узлом (`null + 1`) в правилах RTDB —
  это **ошибка выражения** и отказ записи: любые чтения `lastIdx` /
  соседних транзакций делать только под `.exists()`.
- `child()` требует строковый аргумент: `child(lastIdx.val())` — ошибка,
  нужно `child(lastIdx.val() + '')`.
- Комментарии нельзя держать внутри строки `.validate`: санитайзер
  (`tool/prepare_firebase_rules.py`) вырезает `//` только вне строковых
  значений, а переводы строк внутри правила уже схлопнуты в пробелы —
  «хвостовой» комментарий съедает остаток выражения.
- **Firestore/Supabase/Appwrite**: инварианты 1–3 выражаются строго;
  join'ы позволяют проверить реестр родителя для дочерней модели напрямую
  (строже RTDB-версии) и добавить серверную проверку кворума приглашений.
